DGT_Mv1 — Module and Page API Guide

Prepared 7 October 2026 · Current local source, including uncommitted POS and Swagger changes.

How to use this document

This guide maps the requested 11 modules to their page/component route families. API presence is not proof of production deployment or successful execution. Backend references include associated operations in a shared workflow; verify the named handler when testing an individual button. Preview/gated pages are identified explicitly.

All paths below include /api/v1. Use http://localhost:8181 for local testing. Replace {store}, {dgtId}, or {id} with the appropriate real identifier; DGT-1017 is case-sensitive. Resource {id} placeholders refer to that resource, not always a store.

Most pages first use GET /api/v1/access/stores and GET /api/v1/access/stores/{store}/context. Context controls navigation; backend authorization still applies independently. These shared calls are documented once under Profile.

GET reads; POST creates or performs an action; PUT saves/replaces; PATCH updates selected fields; DELETE removes an association where supported. If-Match and Idempotency-Key requirements are included when declared in the controller. JSON bodies may also carry version/source tokens.

Known contract issue: the local backend globally configures snake_case while some frontend requests use camelCase. A documented endpoint can still fail validation because of this mismatch; this guide does not certify those requests as passing.

API-only and deferred boundaries

Connector POST /api/v1/pos/sales, POST /api/v1/pos/heartbeat and GET /api/v1/pos/configuration are used by the separate connector application, not direct page buttons. POS Settings manages its credentials/configuration through the admin routes above.

Signup/login are outside the 11 requested modules: POST /api/v1/signup-requests submits review; POST /api/v1/client-handling/activate completes setup; POST /api/v1/access/session signs in. The staff portal and its database are separate services.

Generic routes gated by AccessPolicy.check remain blocked. For example, /billing-invoices, /store-subscriptions, /daily-expenses and /departments are not replacements for the connected store-scoped UI workflows.

Shared support APIs may load catalog/options data in child dialogs. Source paths are supplied for those component trees; this document is a page-to-workflow reference, not an assertion that every associated endpoint is invoked on initial page load.
